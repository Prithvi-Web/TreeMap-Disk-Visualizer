# Track U diagnosis — the owner's three problems, reproduced on main (d1def61) on the owner's Mac (30 Sep 2026)

(Recorded by the coordinator from the DIAG helper's final report; the helper could not write .md files. Raw data in this folder: run1…run4 (eld.jsonl, rss.txt, client.jsonl, stats.json, missing-gigabytes.json, prof/*.cpuprofile for runs 2 and 3), e510/shards.jsonl (the 5.1.0 gdu reproduction), tools eld.cjs, sampler.cjs, run-api.cjs, analyze.cjs, prof.cjs, gdu-shards.cjs, ui-instrument.js. Worktree ../wt-diag at d1def61, native 0.5.0.)

## Summary
All three symptoms reproduce on main on this Mac. The largest single cause of the lag, in both main and 5.1.0, is what the UI starts after every scan: a full rebuild of the SQLite index (`buildIndexInBackground`). It walks the whole disk a second time and blocks the server's event loop for minutes. On main the scan itself also walks the disk twice once it passes the 6.19M-row memory ceiling. On 5.1.0 (code + a stage-by-stage reproduction), its gdu engine throws on the oversized `/private` shard, discards what it had, and restarts with the slow built-in walker.

## (1) "Wasn't able to scan my entire disk"
On main: partly reproduces. The scan completes, but:
- Refused folders (high): 981 refused (946 in the walker run). This session lacks Full Disk Access: ~/Library/Mail, Messages, Safari, Suggestions, Biome, ~/.Trash, /Library/Application Support/com.apple.TCC → "Operation not permitted". Main says so; Missing GB carries the bytes as unknown.
- The totals are wrong (high). Run 1 Missing GB vs df (statfs / used 313.2 GB): scanned 428.7 GB; sparse −41.7 GB; open handles 5.16 GB (446); other volumes (Preboot, VM, Recovery, Update) 31.3 GB; snapshots 0; purgeable unknown; refused (982) unknown; Unaccounted −110.2 GB (TreeMap counted more than the volume holds). Over-count: APFS clones counted at full size + the simulator volumes walked through their mount points. Omission: Data-volume root folders not firmlinked to / are never walked (/System/Volumes is never-descend): .Spotlight-V100, .DocumentRevisions-V100, .fseventsd, .TemporaryItems, MobileSoftwareUpdate, sw. Firmlinked folders are not double-counted.
- The counter freezes (high, as a UX cause): when the first walk hits the memory ceiling, the second walk runs silently under Math.max; the counter stood still 65 s (run 1) and ~16 min (run 3). A user sees a hung scan and presses Stop.
On 5.1.0 (code + reproduction): TCC refusals are silent (gdu reported deniedDirs = 0 for every shard; refused folders become silently empty; the total falls short) (high). The fallback resets progress (when the /private shard fails the size check, 5.1.0 zeroes every counter and restarts with the walker; the count drops back toward zero) (high). "Too large to display" is not it: the frame here is 238.6M characters, under V8's 536.8M limit (medium).

## (2) "Scanning for a super long time"
On main: reproduces. Run 1 (low load): 231.7 s for 9,115,094 entries (engine native, fast path bulk, budget auto → balanced). Walk 1 (memory mode) 96 s to hit the 6,187,499-entry ceiling (MEMORY_CAP_ROWS 6.25M minus headroom, nativeMemory.ts); walk 2 (columns path) 128 s; ingest 7.4 s; ~41 % of the scan was the wasted first walk. Run 3: 1,403 s, ceiling at ~430 s; after it the UI polled /result 88+ times. Then the UI's automatic index build of / took another 1,853 s (31 min) at load p50 18: it re-walks the disk with the JS readdir + lstat enumerator (src/platform/base.ts, one lstat at a time within each folder), inserts 9.46M rows into SQLite → index.db 2.63 GB + 364 MB WAL.
Causes ranked: 1 the index rebuild after every scan (high; doubles/triples disk activity; app busy long after "complete"); 2 the memory ceiling and re-walk (high); 3 Balanced budget for a foreground scan (medium; Automatic becomes Eco on battery or thermally serious — matters on a fanless machine); 4 mount points crossed (medium; ~1.18M extra entries).
On 5.1.0 (its gdu v5.36.1 + the unchanged mapper and store; e510/shards.jsonl; load 13–26): /Applications 3.1 s, 22.7 MB JSON, 302,231 entries; /Library 2.1 s, 9.6 MB, 142,809; /System 10.5 s, 32.3 MB, 517,324; /Users 72.2 s, 179.6 MB, 1,643,497; /private 78 s, 592.7 MB (565 MiB), 5,316,292. /private is over MAX_SHARD_BYTES (450 MiB) → 5.1.0 throws and re-walks everything with the Node walker (reading that file as UTF-8 also hits V8's string limit: RangeError measured). Shards run one after another; the counter moves only between shards (frozen ~72 s during /Users, ~78 s during /private). Measured proxy for the fallback walk (main's walker at Turbo, run 4, load p50 15.5): 9,347,504 entries in 434.5 s (21.5k/s), peak RSS 1.98 GB. So 5.1.0 here today ≈ 166 s of gdu work thrown away, then ~7 min of walker, then the same 31-min index build. Caveat: /private's size comes from the engineering scratch folders; whether the owner's 5.1.0 scan hit the cap depends on when they ran it — cannot be known.

## (3) "Glitching and lagging"
On main: reproduces as main-thread stalls (in Electron these freeze the main process: beachball, dead window, no IPC). Attribution from --cpu-prof.
1. The index build (high, largest): event loop blocked 598.6 s of 1,853 s (32 %): 2,744 stalls, 14 over 5 s, 3 over 20 s. SQLite flush transactions 40.8 s and 29.8 s (indexEngine.ts flush / insertMany); 190 s in stalls ≥ 3 s. rollUpSizes: 111.0 s in one block (a synchronous .all() of 9.4M rows, a Map, one update transaction). Heap peaked at 3,764 MB against Node 24's 4,288 MB limit; peak RSS 3.99 GB — under Electron's ~4 GB V8 limit an out-of-memory risk (not verified). After the build the whole-disk FSEvents watcher costs little (6.4 % CPU idle, stalls ≤ 117 ms).
2. Completion burst (high): the columns ingest runs on the main thread (ingestColumns, addNode/writeNode, finalize): 7.4 s run 1, 11.8 s run 3, 40.8 s run 2. The first tree frame is 238.6 MB, 671,545 nodes against a 250k budget (the prune expands whole folders; every node carries its full path). sendPrunedTree runs a full synchronous count pass (0.75 s at load 9, 3.6 s at load 25) then yields only on socket backpressure (stalls ≤ 0.55 s). UI watchdog amplification: it fires /result every 3 s after 6 s without SSE events; keep-alive comments do not count as events; nothing stops a second poll while one is in flight → run 3 serialized the 238 MB tree 4× (2.2–15.8 s each) and abandoned the SSE frame at 108.9 MB; run 2 8×. collectCleanupSuggestions blocked 13.4 s (synchronous visit of every node). file-types 1.8 s, large-folders 1.1 s. Peak RSS at completion 3.2–3.5 GB (run 1: ArrayBuffers 2.1 GB).
3. Page side (run 3, high): JSON.parse of the 238.6M-character tree 1,885 ms, then 954, 1,059, 749 ms for the duplicate responses. finishScan 1,352 ms synchronous incl. indexTree 395 ms for 671,609 nodes; settled after 17.6 s. Renderer heap 233 MB. Once painted the map is smooth: /treemap 61 ms (1.58 MB, 6,089 nodes), draw 10–33 ms, drill-in 32–50 ms, back 46 ms, hover < 0.1 ms. Run 2 (pane visible): the completion task was one 5,184 ms long task.
4. App open (medium): /api/zombie-handles spawns a ps per process: 0.68–1.9 s stall. Startup eagerly loads exceljs, pdfmake and the MCP SDK: 0.56–1.65 s.
During the native walks themselves the loop was fine (max 63–243 ms). Main's walker proxy stalls 22 s in total over its walk (max 973 ms).
On 5.1.0 (code): every shard's JSON.parse + mapping on the main thread (measured /Users 2.56 + 2.23 s, /System 1.5 s); finalize/sumSizes synchronous; the complete frame built as prune objects + one JSON.stringify string in sseSend, synchronous (main's treeFrame.ts notes: +680 MB; not timed here); the same watchdog amplification (the counter does not move during shards, so it polls throughout); then the same index build.

## F. Packaging
A build contains the Rust module only if it exists at packaging time. build.files and build.asarUnpack include native/prebuilt/**. The loader's first candidate is app.asar/native/prebuilt/darwin-arm64/treemap_core.node; Electron's asar layer + dlopen redirect to app.asar.unpacked should load it (inferred, not tested in a packaged app). The second candidate, resourcesPath/native, is populated by nothing. `npm run dist` / `dist:mac` never run build:native — only release.yml:144-149 does. native/prebuilt is gitignored; the owner's checkout holds a 0.5.0 prebuilt from 28 Sep, so a local dist:mac today would ship it; a clean checkout would not, and would scan with gdu or the walker. Not verified: the Electron memory-mode path (storeTakeInto).

## Fix candidates (not implemented)
1. Stop the automatic whole-disk index rebuild, or build the index from the scan's store, off the main thread, with the size roll-up in SQL. Evidence: 31 min; 32 % event-loop blocked; stalls 111, 40.8, 29.8 s; heap 3.76 GB; 2.63 GB database.
2. Size the memory store from df -i before walking, or convert without re-walking, and keep progress visible. Evidence: 96 s of 232 s wasted; counter frozen 65 s – 16 min; 3.2–3.5 GB peak on the columns path.
3. Move ingestColumns/finalize/sumSizes off the main thread. Evidence: 7.4–11.8 s stalls.
4. Bound the first frame for real: don't expand a folder past the budget, drop per-node full paths, yield between chunks. Evidence: 238.6 MB / 671k nodes; 0.75–3.6 s server stall; 1.9 s page parse.
5. Fix the watchdog: one poll in flight; SSE events rather than comments as heartbeats; cache the serialized frame on the server. Evidence: tree serialized 4× (run 3), 8× (run 2).
6. Add a device boundary to the native walker. On macOS 27 here firmlinks share st_dev with / (16777234) and the simulator volumes do not (16777239, 16777247). Evidence: ~1.18M extra entries; Unaccounted −110 GB.
7. Make collectCleanupSuggestions yield or run in a worker. Evidence: 13.4 s stall.
8. Run user-started scans at Turbo, not Balanced/Eco.
9. Make zombie-handles one ps call; lazy-load exceljs/pdfmake/MCP.
10. Missing GB: list the unreachable Data-root folders as unknown lines.
11. buildScanStats hard-codes storageMode: 'memory', even for the columns re-walk.
