**Goal:** an optional second opinion for similar photos. When — and only when — a person has said yes in the TreeMap window, TreeMap downloads one pinned model file once, verifies it, and from then on runs a small vision embedding model offline over the cases the fast tier (Phase 6) finds ambiguous — cluster representatives and near misses, never the whole library. It reports what the model adds **beside** the fast tier's answer, as suggestions a person checks, never inside the clusters that auto-select, the reclaimable figures and the last-copy rule act on. It aims at the master prompt's 0.95 recall on crops of 10 % or less (§5.5) without losing precision, stays inside the resource governor, prefers the Neural Engine on Apple silicon, and leaves every default feature exactly as it was — byte for byte — for everyone who never opts in, including an air-gapped machine.

**Architecture:** everything lives under `src/services/deepTier/` and one route file, `src/api/deepTierRoutes.ts`, whose handlers `require` the rest lazily: nothing in the default path imports ONNX Runtime or the downloader. A small record (`<appData>/deep-tier.json`, written only by `state.ts`, read only through `record.ts`, which asks `isEphemeral()` first) says whether a person consented, to which pinned file, and whether the tier is on. Consent comes from a person through a channel an API caller cannot reach: in the desktop app, the page asks over Electron IPC (`window.treemapDesktop.requestDeepTierConsent`), never HTTP, and the main process raises the app's own native question; in web mode, an 8-character code from `crypto.randomInt` is written only to the server's **controlling terminal** (`/dev/tty`), and only when stdin and stdout are both terminals — never to stdout, a log or a response. `PUT /api/settings` can never grant it. Before the question is asked, a probe child opens ONNX Runtime on a tiny model that ships with the app, so the question names the exact file for the provider that will run it. The only network code in the feature is `modelDownload.ts`: one `node:https` GET of one URL pinned to a Hugging Face commit, streamed to a `.part` file while it is hashed, kept only if its SHA-256 matches the pin. Inference runs in a **child process** (`inferenceChild.ts`, entered through a `.cjs` shim) because `onnxruntime-node`'s `run()` is synchronous on the calling thread (verified, below). The child starts model-free; it loads ONNX Runtime only when there is something to embed, reads and hashes the model file itself (own storage, one module) and hands the same `Buffer` to the runtime. **The child never receives a path and never opens a user's file:** the parent reads every targeted image through Phase 6's verified reader (`readImageVerified` → `imgReadVerified`: a fresh probe, `open_verified`, the read, `still_same()`, with no wait of any kind between the probe and the read) inside Phase 6's byte budget, and posts the bytes. The deep pass starts only from the HTTP near-duplicate route, only on a complete **fast-tier** job: `targeting.ts` picks the representatives and the near misses Phase 6 hands over (`nearMissPairs`), `embeddingCache.ts` answers what it already knows from Phase 5's `content-cache.db` (Node owns it; the child never opens it), the child embeds the rest, and the pass scores exactly the pairs targeting names, in integer arithmetic. **Its results are additive fields** — per cluster `deepCandidates` and `deepRelated`, top-level `deepPairs` and a `deep` block — shown unselected; the fast tier's `files`, representative, `tier`, `confidence`, reclaimable figures, auto-select and last-copy registration are byte-identical with the tier on or off.

### HTTP (all new routes in `src/api/deepTierRoutes.ts`; every body route requires `Content-Type: application/json`, else `415`)

* `GET /api/deep-tier` → `DeepTierStatus` (the `meta` lane: cheap, read from the record; `models.ts` loaded here, lazily).
* `POST /api/deep-tier/consent` `{ intent: 'download' | 'enable' }` (**web mode only**) → `202 { consentId, channel: 'terminal-code', expiresAt, offer }`; refusals `403 CONSENT_REQUIRED` (the desktop app: "ask in the TreeMap window"), `409 CONSENT_PENDING`, `409 DEEP_TIER_UNAVAILABLE { reason }` (no controlling terminal, read-only portable, platform, no model pinned, the probe failed), `429 CONSENT_QUIET { reason }`. The code is never in any response.
* `POST /api/deep-tier/consent/{consentId}/confirm` `{ code }` (web mode) → `202 { jobId }` for a download, `200` status for an enable; `403 CONSENT_CODE_WRONG { attemptsLeft }`, `410 CONSENT_EXPIRED`.
* Desktop app: no HTTP consent at all — `window.treemapDesktop.requestDeepTierConsent(intent)` → `{ ok, status, jobId? }` or the refusal, over IPC (P7-2).
* `GET /api/deep-tier/download/{jobId}/progress` — SSE in `watchJob`'s frame shape: `progress { phase, bytesDone, bytesTotal, filesDone, fileCount: 1, currentPath: displayName }`, `complete`, `error { message }`, `cancelled`, `shutdown`. In the `meta` lane (`META_PATTERNS` gains it).
* `POST /api/deep-tier/download/{jobId}/cancel` — body-less like every existing cancel (the safe direction).
* `POST /api/deep-tier/disable` `{}` → status (anything may switch it off; audited).
* `DELETE /api/deep-tier/model` → removes the model files, the working folder and the `embeddings` rows (own storage, `destructive: false`, the `DELETE /api/index` precedent; audited).
* `PUT /api/settings` with a `deepTier` key → `403 CONSENT_REQUIRED`, "The deep similar-photo check can only be turned on by a person in the TreeMap window (Settings → Similar photos)."
* `POST /api/near-duplicates/deep/start | /pause | /resume | /cancel` body `{ scanId }` → `200 { scanId, status, paused }` · `400 SCAN_ID_REQUIRED` (a missing or non-JSON body) · `404 DEEP_PASS_NOT_RUNNING` (pause/resume/cancel) · `409 DEEP_PASS_NOT_ELIGIBLE { reason }` (start: tier off, legacy tier, job not complete) — non-destructive, `api` lane.
* `GET /api/near-duplicates` — additive, only while the tier is on:
