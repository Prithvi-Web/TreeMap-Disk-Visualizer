**Goal:** exact-duplicate detection that is faster and reads less — BLAKE3 in a governed Rust crate, a sample stage that reads 12 KiB per file, a digest cache that makes an unchanged rescan read nothing — and that is *safer* than today, with the scope of each promise stated as built: **no request can remove the last copy of a duplicate group that this TreeMap process has reported, while that group's scan is held** (a folder the request names is never refused; the MCP server is a separate process with its own record; P5-2), a copy in the Trash or in TreeMap's own storage never counts as the copy that survives (P5-27), a digest that could be stale is never trusted to decide a delete without comparing content (P5-28), a cloud placeholder is never opened (provably: a log of every open, a kernel-level watch on Linux, and the owner's live evicted file), every file that was not read is counted with its reason, and the SHA-256 finder stays as the fallback — held to the same rules wherever Node can hold it, and saying where it cannot (P5-29) — and as the oracle every new group is checked against.

**Architecture:** Node keeps the job, the policy and the cache; Rust does every read. Node buckets the store's files by size (ids only, walking with an explicit stack and yielding to the event loop), drops what the scan already flags (placeholders, links) into `notHashed`, and hands the candidates to `tm-hash` twice, as **the scan root plus paths relative to it**. First a **probe job** — metadata calls only, never an open for data — returns each file's exact identity (24-byte file id, size, `mtime_ns`, `ctime_ns`), whether its data is local *now* (RISKS R71, on the hash threads instead of the JS thread), whether its mount is read-hostile (Linux FUSE and network mounts, macOS non-local and FUSE mounts, Windows remote drives and any file system outside NTFS/ReFS/FAT/exFAT, R2), whether its file system keeps stable ids (so a digest may be cached against them), its clone evidence and its device's queue policy. Node looks the strong identities up in `content-cache.db` (better-sqlite3, one new file beside `index.db`). Then a **digest job** reads only the misses, per device, in inode order, under the process-wide governor (a per-job Eco cap for unattended work): sample digest (BLAKE3 over `size ‖ first 4 KiB ‖ middle 4 KiB ‖ last 4 KiB`), full digest of what still matches, a byte comparison of large groups. **Every data open is relative to a descriptor of the scan root** (macOS `O_NOFOLLOW_ANY`, Linux `openat2` `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS`, Windows a `\\?\` path whose final path is checked on the handle), so a symlinked ancestor above the root (macOS `/var` → `/private/var`) is followed as the scan followed it and no link below it is; before the first read of **every** stage the descriptor is checked a regular file, its data still local (macOS `SF_DATALESS`, Windows recall attributes) and its identity still the probe's; after the last read it is re-stated, so a file that changed leaves its group and is counted. Node writes the new digests back, builds the groups (hard-link names collapsed by the hasher's own `(dev, ino)`, clones one storage unit, `reclaimable` in allocated bytes, copies in the Trash or app-data sorted last and never the keeper, the upper-bound caveat surfaced), and registers **every** group's membership with the identity and evidence the hasher saw (read now or from the cache; strong or weak) — which is what `moveToTrash`, the only delete pathway, consults to refuse the last copy against the live disk, by file identity rather than spelling, comparing content under the group's lock wherever the evidence could be stale. Both jobs follow the scan's start/poll/pause/resume/cancel/take shape (P3-1), are polled at 100 ms, and pause with the scans when the machine sleeps. Without the module, or when a native job fails, the SHA-256 finder runs, says so in `engine`/`engineReason`, and is held to P5-29.

| P5-1 | **The last-copy rule lives in `moveToTrash` (`src/services/cleaner.ts:175`), the only delete pathway, and in every dry-run planner.** A requested path that is a member of a known duplicate group is refused with code `LAST_COPY` when that group has **no survivor**. A survivor is a member that (a) is not a file the request names — compared by **file identity** (`(dev, ino)` from the group's own identity source, P5-6), never by spelling, so an NFC request for an NFD name, `/tmp/x` for `/private/tmp/x` and two names of one inode are all the same file; (b) does not lie under a folder the request names — its ancestor directories compared by identity with the named folders; (c) is not in the Trash or TreeMap's own storage (P5-27); (d) still stats — live, immediately before the trash, under the group's lock — to the identity recorded when its group was proven; and (e) where either file's evidence could be stale, has the same content as the requested file, compared under the lock (P5-28). Refusal is per path (it lands in `failed[]` / `skipped[]` / the run's `skipped`, like `trashRefusal` and the capsule's too-large items), and the rest of the request proceeds. | P5-6 | **Identity comes from the hasher's own stat, twice, and is strong only where the file system keeps stable ids.** The probe job reads it with metadata calls that never open the file for data, relative to the root descriptor (macOS `fstatat(AT_SYMLINK_NOFOLLOW)` + `getattrlistat(FSOPT_NOFOLLOW)`, Linux `statx(rootfd, rel, AT_SYMLINK_NOFOLLOW)`, Windows `FindFirstFileExW` then a `FILE_READ_ATTRIBUTES` handle with `FILE_FLAG_OPEN_REPARSE_POINT` for `FILE_ID_INFO`/`FILE_BASIC_INFO`/`FILE_STANDARD_INFO`) — cost: one metadata call per candidate (two on Windows), measured in T17b. The digest job `fstat`s the opened descriptor before the first read of every stage: `(dev, ino)` must be the probe's, else `pathChanged`; size, `mtime_ns` and `ctime_ns` must be the probe's, else `changedWhileHashing` — and nothing is written back to the cache for it; again after the last read (unchanged and bytes read = size, else `changedWhileHashing`). ## Open questions for the owner

1. **The change time in the cache key?** A file rewritten with its old mtime restored (`cp -p`, `rsync -t`) keeps size and mtime; without the change time its stale digest would be read as current and could make a false group below the byte-compare threshold. **Recommend: yes** (P5-15 builds it in; dropping it later is a schema bump). The guard's content comparison (P5-28) is the backstop either way.
2. **The UI's minimum size.** It is 100 KB today (not 1 KB as DESIGN assumed). **Recommend:** keep 100 KB selected, add a "4 KB" option; the API, MCP and bench stay at 1,024 B.
3. **A folder that holds the last copies of a group.** **Recommend:** never refused by the last-copy rule (P5-2) — the rule protects copies the person selects, not folders they clear — while its members still count as removed for everything else in the request.
4. **Whole-group refusal.** A request naming every copy trashes none (the toast's rule). **Recommend:** keep it; if Autopilot should clear duplicates unattended, add a later `dupe:extra` value ("not the newest copy") rather than let the server pick a keeper.
5. **Offload of every copy.** **Recommend:** allowed, because each original has a verified copy at the destination when it is trashed (P5-2).
6. **Hashing network and FUSE mounts.** **Recommend:** no opt-in in Phase 5; they are counted and named in `notHashed`. Phase 8 keeps it closed too (its P8-25); an opt-in would need its own safety review.
7. **Rows the gate may miss.** The bytes-read row will be MISSED on a first run (≈ 3.26× ceiling on this corpus by arithmetic), and the rescan, budget or latency rows may be. The gate then reads "not passed: owner decision pending" (P5-31) and Phase 6 waits. **Recommend** (to be decided once the figures exist): accept the bytes row as "MISSED, measured N×, ceiling ≈ 3.26× on this corpus by arithmetic; the cached rescan requests 0 bytes"; judge the rescan row against the native first run with the legacy comparison beside it; decide any other MISSED row on its figure.
8. **The cache's cap.** **Recommend:** min(256 MiB, 1 % of the app-data volume), no writes below max(2 GiB, 5 %) free.
9. **The last-copy rule's reach.** It refuses `LAST_COPY` on every route that reaches `moveToTrash` — DELETE /api/files from any view (Largest Files, queries, the Duplicates view), MCP `trash_paths`, cart commits, Autopilot, compression, snapshot restore — whenever a job in this process has reported the group, and adds `refused`/`survivedBy`/`withFolder` to the dry runs. That changes the documented behaviour of `DELETE /api/files` and `/api/cart/commit` (MP §15: ask before changing a public API; docs-risks C-12). **Recommend: every route** — a copy's last survivor is as lost from Largest Files as from the Duplicates view. T1a starts after the answer; a narrower answer is a route list in the guard, recorded in DESIGN §10.
10. **Should "hide from cleanup suggestions" also bind Autopilot's query and custom policies?** Today it binds only the `suggestion` kind (`autopilot.ts:453-456`), so a `dupe:` query policy would clear duplicates inside a folder the person hid from suggestions. **Recommend: yes, for every query and custom policy**, as its own fix (with a test per kind and the skips named in `skipped`) landing before T15's second half; if no, AGENTS.md says a folder note is the way to fence a folder off from Autopilot.
11. **Materialisation off for the whole process?** If the thread-scope `IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES` belt clears the governor's QoS (T8 measures it), the process-scope setting would still stop any in-process read from downloading a dataless file — but it also makes previews, thumbnails and the duplicate viewer fail on such a file instead of downloading it. **Recommend: yes** — TreeMap never wants a download, and those readers already refuse placeholders through `stillLocal`; the setting would make the refusal hold even for a file evicted after the check.
