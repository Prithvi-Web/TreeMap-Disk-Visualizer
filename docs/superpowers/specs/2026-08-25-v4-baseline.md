# TreeMap v4 — the baseline

**Recorded:** 25 August 2026, against commit `2d47e98` (Release v3.2.2), before
a line of v4 code existed.
**Machine:** Apple Silicon MacBook, `darwin-arm64`, Node v24.16.0, a normal
desktop session — **not** a quiet box.

This is the "before" that every v4 phase is measured against. Its one rule is
the project's own: **a number without the load it was taken under is not a
claim about anything.** Every figure below carries its load average.

The first full run of this session failed a single test:

```
✖ an external create, resize and delete each land within 2 seconds
  tests/indexEngine.test.ts — an external create never landed in the index at all
```

This is the A1 live-index watcher flake that `HANDOFF.md` already documents. It
was diagnosed rather than assumed, in the order the traps section demands —
read the failing name first, then investigate:

- Isolated, it passes **3 / 3, in ~1.28 s each**, against a 15 s timeout.
- The failing full-suite run took **19 s**; the immediately following clean run
  took **11.4 s**. The watcher starved under load.
- A second full run: **0 failures**.

Recorded here so a future session does not re-diagnose it. It is not a code
defect, and it was not "fixed".

## 3. Memory — `scripts/bench-store.ts`

Budget: **≤ 56 bytes/node**.

| Nodes | Build | Throughput | **bytes/node** | prune → 250k | Peak RSS | Load |
| --- | --- | --- | --- | --- | --- | --- |
| 1,000,000 | 317 ms | 3,157,246 /s | **49.3** | 158 ms | 173.6 MB | 3.75 |
| 5,000,000 | 1,482 ms | 3,374,457 /s | **51.7** | 152 ms | 369.4 MB | 3.61 |

**Headroom at 5M: 4.3 bytes/node.** That is the entire budget for every
per-node field v4 might be tempted to add to the store — which is a large part
of why the fact layer keeps facts in a side table keyed by path instead.

> **Trap, paid for during Phase 0.3.** These figures need `--expose-gc`, and
> **tsx re-spawns node without forwarding the outer process's V8 flags.**
> `node --expose-gc <tsx-cli> bench-store.ts` therefore measures an unsettled
> heap and reports **~123 B/node** against a true 50.9. The flag must come
> *after* the tsx entry point. `bench-store.ts` warns when `global.gc` is
> missing; `bench-v4.ts` now treats that warning as "no measurement" rather
> than reporting the number.

## 4. Scan throughput — the fixed fixture

Fixture: **50,000 files in 100 folders**, deterministic sizes, rebuilt only when
absent. Engine: **`gdu-turbo`**. Eleven runs, one warm-up discarded.

| Figure | Value |
| --- | --- |
| Median | **1497.9 ms** |
| Throughput | **33,449 items/s** over 50,102 items |
| Resolution (2 SE of the median) | **± 1.0%** |
| Observed range | 5.1% |
| Load at start / end | 2.41 / 3.07 / 3.13 → 2.51 / 3.03 / 3.12 |

Recorded to `scripts/bench-v4-baseline.json`. Guarded by platform, engine and
fixture size: another machine, or a run that falls back to the walker engine,
gets an honest "re-record" rather than a percentage that means nothing.

### Why the resolution figure is here at all

§2.5 budgets scan throughput at **"no more than 2% slower than baseline"**. That
is close to this machine's noise floor, and the first version of the harness
proved it: using max-minus-min as the noise estimate, **unchanged code** scored
`+2.3% against a 2.6% floor`. The budget was below the resolution and could
never have caught anything.

The median's 2-SE band from an interquartile range — robust to a single
scheduler hiccup — puts the resolution at **± 1.0%** over 11 runs, which is
under the 2% budget. The budget is real now. When the machine is busy the band
widens and the verdict becomes INCONCLUSIVE, which is the honest answer rather
than a coin flip.

One baseline was recorded and **discarded**: load spiked 3.54 → 5.24 mid-run and
the range reached 22.1%. A baseline taken under load makes every later
comparison generous, which is the opposite of a gate.

### For reference — the real-world figures from v3

From `HANDOFF.md`, on this same machine, for scale:

| Figure | Measured | Load |
| --- | --- | --- |
| Whole disk `/` | 1,411,715 items in 16.4 s (~85,900 items/s) | 3.13 → 4.61 |
| Home folder | 458,661 items in 9.1 s (~50,300 items/s) | 3.27 |
| `readTree` | 250,000 nodes in ~790 ms (~316k nodes/s) | 4.63 |

The bench fixture reads *slower per item* (33k/s) than the real disk (86k/s)
because `gdu-turbo` parallelises across top-level folders and the fixture has
only 100 of them, all small. That is a property of the fixture, not a
regression — and it is why the gate compares the fixture against itself and
never against the disk figures.

does not guess:

| Budget | Limit | Why not here |

| Main-thread block, single UI action | ≤ 50 ms | Same. `refreshCartButtons`' own comment documents why it matters — a 30.5 ms block was worth fixing. |

Nothing has been drawn yet, so none of them has a first reading. Phase 6 is
where they acquire one.
